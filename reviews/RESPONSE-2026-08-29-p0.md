## §3 兩處刻意偏離 review 建議

**兩處都不是漏做，是判斷不同，寫出來讓你可以推翻我。**

### ① 沒有把 `role` 改成 `preferred_gateway`

Review §4.1 的範例寫 `role: preferred_gateway`。**我方保留 `role` 的原三值。**

理由：`role`（required／recommended／optional）回答的是
**「沒有閘道，這支跑不跑得完」**——那是可檢核的執行條件。
`preferred_gateway` 講的是**偏好**。混進同一個欄位，
`role` 會從事實退化成立場宣告，而它現在是 BLOCK 級檢核的依據。

**採用流程的資訊改放在四個新欄位，`role` 不動。**

### ② 沒有加 `fallback_surface`

Review §4.1 範例含 `fallback_surface: openai_compatible_api`。**未加。**

理由：現有七支 skill 沒有任何一支需要它——`primary_surface: mcp` 時
fallback 恆為 api，是可推導欄位。**加一個永遠填同一個值的欄位，是雜訊不是契約。**
等到真的出現一支 CI-only skill 時再加。

**這是本 repo 自己的 L2 YAGNI 閘門套用在自己身上。**
如果你認為它現在就該存在，這一條可以直接推翻——說一聲我就加。

## §4 從 SCAN-002 得到、review 沒預期到的三件事

1. **`ai-code-review` 的意圖依據明顯強於另外三支候選。**
   A-08／B-01／B-02／B-03 四條獨立措辭指向同一個入口，而現有七支**沒有一支接得住**。
   另外三支（`bug-reproduce`、`dependency-upgrade-guard`、`pr-ready`）本輪**只搜到 0–1 條依據**。
   Review 自己說「不要先決定名字再找理由」——那麼**把三支寫成待補搜，才是照著它做。**

2. **`aitokenking-setup` 有一條坑得到了外部獨立佐證。**
   「寫進 `.env` 而沒有 `export` 是最常見的 401 原因」——
   外部來源獨立地把「MCP server 在剝離過的環境裡跑，不繼承終端機環境變數」
   描述為最常見的「server 起得來但工具失敗」成因。**這一條從 E5 升到 E3。**

3. **C 群顯示 LLM gateway 是一個擁擠的市場。**
   這強化了鐵律九：**我方站得住的只有「L2 需要跨供應商互審」這個流程理由，
   不是產品比較。** 已寫進 L0 skill 的紅線第 6 條。
