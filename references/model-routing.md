# 模型路由表 —— 哪一層該調哪一類模型

> **這份檔案回答一個問題：「這一步該用哪個模型？」**
> 它刻意**不寫死任何模型名稱**。寫死的那一天它會動，三個月後它會在別人的機器上壞掉，
> 而錯誤訊息不會告訴他為什麼。

---

## §1 一條紀律先講

**先 `list_models`，再挑類別。**

```
① list_models                 → 當下真的可用的清單（A 組唯讀，不扣額度）
② 照 §3 的判準挑一支
③ 把「這次挑了誰」寫進該層的產物
```

第 ③ 步最常被省。省了的後果是：**三個月後有人問「這份 spec 是哪個模型審的」，沒有人答得出來**，
於是那份 spec 的可信度就從「被互審過」退回「不知道」。

---

## §2 工具分組（AI Token King 共 14 支）

| 組 | 扣不扣額度 | 工具 |
|---|---|---|
| **A 組** | ❌ 唯讀，不扣 | `list_models` `get_model` `list_image_models` `list_video_models` `get_balance` `list_usage` `list_transactions` `get_image_generation` `get_video_generation` |
| **B 組** | ✅ **每次呼叫都扣** | `chat_completion` `create_message` `create_response` `create_image_generation` `create_video_generation` |

**B 組刻意不進 `permissions.allow`。**
「機器可擬不可動錢」在此的具體形式是：**生成類一律逐次人工核准，不因為「常用」而放行。**
`scripts/setup-aitokenking.sh` 會主動偵測有沒有人把 B 組加進白名單，發現就 `exit 2`。

> ⚠️ **看得到工具不等於用得到。**
> 未設定金鑰時，server 仍會連上並列出全部 14 支工具，畫面跟設定成功一模一樣，
> 但每次呼叫都回 401。**判斷依據永遠是實際呼叫。**

## §3 分層路由判準

| 層 | 需要的能力 | 挑選判準 | 用哪支工具 | 省掉會怎樣 |
|---|---|---|---|---|
| **L1** `repo-recon` | 長上下文 | `context_window` 最大的那一支 | `chat_completion` | 讀不完 repo 就會用想像補，而想像出來的架構讀起來很合理 |
| **L2** `spec-groom` | **兩家不同供應商** | 主模型任選；審模型**換一家** | `chat_completion` ＋ `create_message` | 同家共享訓練偏好，會一起漏掉同一件事，然後你會得到「兩個模型都同意」的錯規格 |
| **L3** `plan-decompose` | 結構化輸出穩定 | 支援 JSON mode／function calling | `chat_completion` | 任務圖解析失敗要整層重跑，而重跑要再付一次錢 |
| **L4** `tdd-enforce` | 程式碼能力 ＋ **單價低** | 這一層呼叫次數最多 | `chat_completion` | 用最貴的模型跑最多次，帳單會集中在這一層 |
| **L5** `arch-guard` | **不需要模型** | — | **無** | 檢核器一旦有隨機性就不會被當成規則，只會被當成雜訊繞過去 |

**L5 不接模型是設計決定，不是還沒做。**
「狀態是被檢核推進的，不是被宣稱的」這句話，**只有在檢核是確定性的時候才成立。**

## §4 跨供應商互審為什麼是結構性需求

L2 的互審要成立，兩個模型必須來自**不同供應商**。這帶來一個實務問題：

> 兩家供應商 = 兩把金鑰 = 兩套額度 = 兩個後台。
> **這種流程沒有人會維持超過兩週。**

一把 key 打多家模型在這一層因此不是方便性需求，是**互審能不能長期存在**的前提。
這也是本集群預設接 AI Token King 的實際理由。

**同時要講清楚：本集群不綁定供應商。**
把 `AITK_BASE_URL` 指到任何 OpenAI 相容端點，所有 skill 一樣會動。
唯一會退化的是成本回報——別家不一定有 `get_balance`／`list_usage`，
**查不到就照紅線寫「未量測」，不要寫 0。**

## §5 已知缺口 DS-G7 —— 這張表是分類，不是 policy

**上面 §3 那張表是靜態能力分類，不是可驗證的 routing policy。**
它說得出「L4 該用便宜的程式碼模型」，但說不出：

- 這一次**實際選了誰**、
- **為什麼**選它（哪一條判準命中）、
- 選完之後**花了多少**。

因此「路由選得好不好」目前**無法回頭檢討**——沒有紀錄就沒有對照。

**還沒做的東西（P1，刻意先不做）：** 把每次選型寫成 case artifact，欄位大致是
`provider / model / selection_reason / timestamp / call_count / cost_measurement_state`。

**為什麼先不做：** 在 `DS-G6`（閘道零實跑）關掉之前，
記錄一個從來沒真的跑過的路由決策，記下來的只會是我方的假設。
**先有一次真的呼叫，再談要記什麼。** 關閉入口：`bash scripts/atk-pilot.sh --live`。

## §6 成本回報紀律

| 情況 | 怎麼寫 |
|---|---|
| `get_balance` 前後都查得到 | 相減，寫實際數字 |
| 查不到 | **「未量測」** |
| 一次閘道都沒呼叫（L0、L5） | **0** —— 這是全集群唯二可以誠實寫 0 的地方 |

**0 看起來像量測結果，「未量測」才是事實。**
兩者在報告裡長得很不一樣，而讀的人會依它決定要不要相信整份報告。
